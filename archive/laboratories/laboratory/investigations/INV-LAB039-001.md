## Executive Summary

This investigation examined Grafana issue #116074 where manually set labels on alert rules do not appear in the `$labels` namespace when notification messages are interpolated. After thorough code analysis, a potential root cause has been identified in the label expansion pipeline.

---

## Issue Description

**What happened**: When setting a custom label manually in an alert rule (e.g., `environment: production`), this label does not appear in the `$labels` namespace that is interpolated into the notification message.

**Expected behavior**: The manually set label should be present in the labels namespace.

**Reproduction steps**:
1. Set an alert and statically set a label (e.g., `environment: production`)
2. Use `{{ $labels }}` in the alert description
3. Wait for alert to fire
4. Inspect alert description - the `environment: production` tuple is missing

### Code Flow for Labels

```
1. Alert Evaluation
   └─> newState() [state/state.go:83]
       └─> expandAnnotationsAndLabels() [state/cache.go:124]
           ├─> Template data created with: mergeLabels(extraLabels, resultLabels)
           ├─> Rule labels expanded using this template data
           └─> Final labels assembled: extraLabels + ruleLabels + resultLabels

2. Alert to Notification
   └─> StateToPostableAlert() [state/compat.go:38]
```

### Label Expansion Pipeline (cache.go:124-209)

```go
func expandAnnotationsAndLabels(...) (data.Labels, data.Labels) {
    // Step 1: Handle reserved labels in result
    resultLabels := result.Instance
    // Reserved labels are renamed to avoid conflicts
    
    // Step 2: Create template data
    templateData := template.NewData(mergeLabels(extraLabels, resultLabels), result)
    
    // Step 3: Expand alert rule labels
    labels, _ := expand(ctx, log, alertRule.Title, alertRule.Labels, templateData, ...)
    
    // Step 4: Assemble final labels
    lbs := make(data.Labels, len(extraLabels)+len(labels)+len(resultLabels)+len(errorLabels))
    
    // extraLabels added first
    // errorLabels added
    // rule labels (expanded) added - may overwrite extraLabels
    // resultLabels added last - will NOT overwrite rule labels
}
```

### Potential Root Cause

**Finding**: In `expandAnnotationsAndLabels()` (cache.go:158), the alert rule labels (`alertRule.Labels`) are expanded using template data that only contains `extraLabels` and `resultLabels`:

```go
templateData := template.NewData(mergeLabels(extraLabels, resultLabels), result)
labels, _ := expand(ctx, log, alertRule.Title, alertRule.Labels, templateData, ...)
```

The `$labels` variable available during label template expansion only includes:
- Extra labels (namespace UID, alert name, rule UID, folder title)
- Result labels (from query evaluation)

It does NOT include other manually set labels from the alert rule itself.

### Evidence

1. **Template Variables** (template/template.go:137):
   ```go
   tmpl = "{{- $labels := .Labels -}}{{- $values := .Values -}}{{- $value := .Value -}}" + tmpl
   ```
   The `$labels` is set to `.Labels` from the template data.

2. **Template Data Creation** (cache.go:154):
   ```go
   templateData := template.NewData(mergeLabels(extraLabels, resultLabels), result)
   ```
   Only `extraLabels` and `resultLabels` are merged into the template data.

3. **Final Label Assembly** (cache.go:174-209):
   The final `lbs` does include all labels, but this happens AFTER the template expansion.

| Severity | Medium |
|----------|--------|
| User Impact | Users cannot reference their custom labels in notification templates via `$labels` |
| Scope | All alert rules with manually set labels |
| Workaround | Use specific label references like `{{ $labels.environment }}` instead of `{{ $labels }}` |

---

## Recommended Fix

The fix should ensure that the `$labels` template variable includes all labels that will be present in the final alert, including manually set rule labels.

**Option 1**: Merge all labels (including alertRule.Labels) before template expansion
**Option 2**: Document the current behavior and recommend using specific label references

Given the scope of the change, Option 1 is preferred for a proper fix.
